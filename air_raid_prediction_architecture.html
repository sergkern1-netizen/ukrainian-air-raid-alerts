1. System Architecture Overview

Five-layer architecture optimized for resilience under extreme conditions:

Data Flow: Sources push/poll into Kafka cluster (2 brokers, 3x replication). Spark consumes, computes features, writes hot paths to Redis. Cold queries hit TimescaleDB (49 data sources × 10+ features). Geospatial queries use PostGIS for oblast-level alerts. Feature store (Redis) serves inference at <50ms latency. Fallback: rule-based alerts (missile type + trajectory + distance to cities).

2. Technology Stack & Rationale

TimescaleDB

Time-series storage (alerts, weather, missile launches). 1M+ points/sec ingest. Handles gaps during network outages (backfill once connected).

PostGIS (PostgreSQL)

Geospatial queries (oblast boundaries, nearest cities). Sub-100ms polygon containment checks. Stands as fallback when feature store fails.

Redis Cluster

Feature cache (hot path <50ms). Handles 10k req/sec peak. Async replication to disk. Auto-failover across 3+ nodes.

DuckDB (OLAP)

Historical analytics & model training. Compressed columnar storage. Sidestep network by running local inference on cached data.

Apache Kafka

Ingest backbone. 2-broker cluster, 3x replication. Survives single broker outage. Consumer lag monitoring (alert if >5min behind).

Spark Structured Streaming

Real-time feature computation. Micro-batch semantics (1-5sec windows). Exactly-once processing to avoid double-alerts.

Trade-off Analysis

  • Latency vs. Durability: Redis for <50ms inference; TimescaleDB for durability. Kafka ensures replay if Redis fails.
  • Cost vs. Redundancy: 2-broker Kafka (not 3) acceptable because sources re-send failed payloads. 3x replication in Kafka itself adds safety.
  • Complexity vs. Resilience: Accept complexity of multi-DB (TimescaleDB + PostGIS + Redis) because no single DB handles all access patterns at required latency.

3. Real-Time Streaming Pipeline

Challenge: Track "alert in progress" state across 49 regions while handling 8-10 req/min rate limit on alerts.in.ua API.

Ingest Strategy

  • Kafka Topics:
    • alerts-raw (alerts.in.ua polling, 90sec interval max)
    • telegram-webhooks (push from Telegram bots, rate-limited)
    • weather-feeds (NOAA, Meteosource batch, hourly)
    • satellite-imagery (batch daily, triggers feature recompute)
  • Producers: Dedicated Lambda-like containers poll alerts.in.ua at 2 req/min, spread load across 4 containers (8 req/min total, under limit). Exponential backoff if rate-limited (503 response).

State Management & Windowing

Spark job maintains state:
  - Alert cache: regionId -> {start, lastUpdate, severity, trajectory}
  - State TTL: 24h (stale alerts auto-expire)
  - Deduplication: deduplicate within 60sec window

Output:
  - NEW_ALERT: timestamp, region, confidence
  - ALERT_UPDATE: severity change, trajectory refined
  - ALERT_END: confidence drops below threshold

Fault Tolerance

  • Kafka broker failure: Rebalance (automatic), no data loss (3x replication).
  • Spark driver failure: Kubernetes restarts pod, resumes from last checkpoint (S3-backed).
  • alerts.in.ua down: Fall back to Telegram bot messages + cached baseline model. Resume API polling when back online.

4. Model Serving Strategy

Dual-Mode Inference

  1. Online Path (real-time):
    • Features from Redis + hot Kafka stream
    • 3-model ensemble (gradient boosting + neural net + rule-based)
    • Latency SLA: <100ms p95, <50ms p50
    • Deployed as stateless Python service (Uvicorn + Ray Serve)
  2. Fallback Path (if online fails):
    • Rule-based: missile_type + trajectory + distance_to_nearest_city
    • Zero ML dependencies; responds in <10ms
    • Automatic activation if Redis latency >200ms or model inference fails 3x

Model Deployment

  • Nightly retraining: Run on DuckDB + historical data. Test on holdout week (measure precision/recall). If metrics degrade >1%, don't deploy (alert ops).
  • Canary roll: 10% traffic for 1h, compare alert volume vs. baseline. If discrepancy >5%, rollback automatically.
  • Versioning: Models stored as Docker images with git commit + model version. Kubernetes manages A/B routing via sidecar.
  • Uncertainty quantification: Return confidence intervals (e.g., 85-92% alert probability). Threshold at 80% for public alerts, 75% for researcher alerts.

5. Resilience & Disaster Recovery

Network Outage (hours)

Systems continue with cached data. Kafka local storage keeps 24h backlog. Resume sync when connectivity returns (backfill gaps from TimescaleDB).

Rate-Limit Hit

Switch to raid.fly.dev backup API (hits it at 2 req/min instead). Alerts delayed 90-180sec but maintain continuity.

Model Serving Failure

Automatic fallback to rule-based alerts. Ops notified immediately. Manual model restart or rollback available in <30sec.

Data Loss Prevention

TimescaleDB: WAL to EBS (6h retention). S3 nightly backups (daily snapshots). Kafka: 24h retention on all topics.

RTO/RPO Targets

  • RTO: 2-5 minutes (Kubernetes auto-restarts, Kafka rebalance)
  • RPO: 60 seconds (S3 backups, Kafka checkpoint)
  • Alert latency (normal): 10-30sec from detection to user
  • Alert latency (degraded): 2-3min (Telegram bot only, no model)

Health Monitoring KPIs

  • Kafka consumer lag (alert if >5min)
  • Redis cache hit rate (alert if <85%)
  • TimescaleDB replication lag (alert if >10sec)
  • Model inference latency p95 (alert if >150ms)
  • Alert.in.ua API availability (alert if <99.5% in 5min window)
  • Fallback rule-based alert rate (spike indicates model failure)

6. Deployment & Operations

Infrastructure

  • Orchestration: Kubernetes (EKS or self-hosted). Spans 2+ availability zones within safe region (Poland, Romania, or EU).
  • Node pools:
    • ingestion (CPU-optimized): Kafka brokers, Spark executor nodes
    • serving (balanced): Model serving, Redis, feature API
    • batch (GPU-optional): Model training, feature recompute
  • CI/CD: GitHub Actions. Test models in Docker before push. Run integration tests (real Kafka, test data) before production deploy.
  • Secrets: Sealed secrets (K8s native). API keys for alerts.in.ua, Telegram, Meteosource in AWS Secrets Manager.

7. Scalability Strategy

Current Capacity (Day 1)

  • Ingest: 1000s events/sec (49 regions × 20 features/sec)
  • Inference: 5000 req/sec p99 (spikes to 15k during major strike)
  • Storage: ~500GB/year (time-series + geospatial)

Scaling Levers

  1. Kafka: Increase partitions (currently 48, max 144 for 49 regions). Add brokers if throughput >10k msg/sec.
  2. Spark: Horizontal scaling via executor pods. Auto-scale based on Kafka lag (if lag >5min, +10 executors).
  3. Redis: Cluster mode (16 shards). Cache eviction policy: allkeys-lru (100GB heap per shard).
  4. Model Serving: Ray Serve auto-scales (0-100 replicas based on request queue). Max latency target: 200ms p99.
  5. TimescaleDB: Partitioning by region + time (yearly). Compression for data >30d old.

Geographic Expansion Path

  • Phase 1 (Ukraine only): 49 regions, 1 cluster
  • Phase 2 (Poland, Moldova): Add 25 regions, same cluster (scale Kafka × 2)
  • Phase 3 (EU-wide): Multi-cluster with CDC (Change Data Capture) replication. Route requests to nearest cluster.

Summary: Key Decisions

Architecture Principles

  • Assume failure: Every component can fail independently. Always have a fallback.
  • Degrade gracefully: Lose features (satellite imagery), not alerts. Fall back to rules over silence.
  • Optimize for latency under load: 10-30sec alert delivery during normal operations; <2min during degradation.
  • Embrace immutability: Models, data pipelines versioned. Rollback always possible.
  • Monitor obsessively: Alerting thresholds tuned to conflict environment (high variance acceptable; missed alerts unacceptable).
